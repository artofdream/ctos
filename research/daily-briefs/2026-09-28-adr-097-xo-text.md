# 2026-09-28 — ADR-097: EL0 app text execute-only (proposed; merge requires sponsor rev 4 written accept)

- **Ask:** milestone 3 (sponsor-approved, $0; relayed by the DSO): split app rodata out of the app code page so EL0 app text is execute-only, removing the ADR-094 limit “EL0 can read its own code bytes”. One branch, one PR, stacked on #149; DSO/sponsor merge (ADR-002).
- **Design ([ADR-097](../../docs/03-adr/ADR-097-el0-execute-only-app-text.md)):** every app's `.rodata` now sits on the ELF-header page (`app-hdr`, `0x80000000`, EL0 RO + NX, already allowlisted). `.text` sits alone on `app-text` (`0x80002000`), mapped EL1 RO / EL0 none / UXN=0. **Still five slots**, labels unchanged, `el0-reach:` lines byte-identical. `build.rs` and the loader both enforce the layout.
- **Probes:** EL0 load of its own text → permission fault (`xo: el0-read-text fault … esr=0x9200000f … dfsc=perm-l3 got=0x0`); EL0 still executes and reads its rodata (`xo: el0-exec ok … got=0x584f524441544131`, `xo: el0-uart rodata-str ok`); `uart_write` of a text pointer refused (`xo: sys-read text denied … checks=1`); inventory shows the new layout and counts the UXN=0 page (`reach=uxn`, XO plant caught); `xo: ok … slots=5`. All fail-closed in `scripts/qemu-smoke.sh`; the `el0-leak-probe` build now also maps text EL0-readable and undoes the PAN fix, and must be caught.
- **Probed this session:** full `./scripts/qemu-smoke.sh` on the box (QEMU 10.0.13 TCG): `qemu-smoke: ok`, 152 tests including `el0_app_text_is_execute_only`, A9 cross-update to the prior OS still `slot:ok`, leak build caught. Ten tampered logs against the ADR-097 block all failed; the unedited log passed.
- **Surprise 1 (EPAN):** `ID_AA64MMFR1_EL1.PAN`=2, no FEAT_EPAN. With PAN set, an EL1 load of the XO text page does **not** fault (it reads the code word). The ADR-091 clause “PAN is enabled and EL1 faults on EL0 memory” is therefore not literally true for that page. ADR-091 is not edited; merge requires a sponsor rev 4 written accept (candidate wording in ADR-097).
- **Surprise 2 (pre-existing PAN gap, fixed, separable):** `SCTLR_EL1.SPAN` was 1 and `return_from_el0` resumed with SPSR.PAN clear, so PAN was clear while the kernel handled EL0 exceptions and after EL0 trips. The boot-time `pan: el1-fault` probe could not see it. Fixed (SPAN=0, SPSR.PAN on return); live check `xo: pan live-syscall pstate-pan=1 sctlr-span=0`; ledger correction row. *Update 2026-09-29:* split out as [ADR-098](../../docs/03-adr/ADR-098-pan-held-during-el0-exceptions.md) (PR #151, based on `main`); #150 now merges that branch.
- **Not claimed:** any change to the ADR-091 sentence; real hardware; multi-core; side channels; EL1 unable to read app text (it can).
