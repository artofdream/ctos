# ADR-082 research brief — B1 QEMU `TYPE_NMI` → SError

- Date: 2026-09-19 CEST
- Host: agent-box (`grok-bot-vm-401670533`)
- QEMU: `qemu-system-aarch64` **10.0.13** (Debian `1:10.0.13+ds-0+deb13u1`)
- Accel: TCG only
- Default smoke CPU: `-cpu cortex-a76` (ADR-079)
- Sponsor decision: **B1** (not B2/B3), ~08:58 CEST

## Question

Can ctos pin a newer / rebuilt QEMU so `virt` exposes `TYPE_NMI` and `inject-nmi` delivers **async SError** to standing EL0 under TCG, allowing smoke to require `el0: serror`?

## Live probe

Script: `scripts/qemu-nmi-probe.py`. Raw log: `2026-09-19-adr-082-b1-qemu-nmi-probe.txt`.

All rows (default a76, a57, GICv3, max, virtualization=on, secure=on): QMP `inject-nmi` → `machine does not provide NMIs`.

## Upstream

- `hw/arm/virt.c` on **v10.0.0**, **v10.1.0**, and **master** (2026-09-19 fetch): **no** `TYPE_NMI` / `nmi_monitor_handler`.
- FEAT_NMI in tree = architectural interrupt NMI (`ARM_CPU_NMI`), not async SError.
- 2020 “Simulate NMI Injection” series (virt → `ARM_CPU_SERROR`) **did not land**.
- `CPU_INTERRUPT_VSERR` is virtual SError for EL2, not host QMP inject.

## CI pin verdict

| Path | Unlock? |
| --- | --- |
| Apt newer qemu | No — packaged trees lack virt `TYPE_NMI`→SError |
| Build upstream master | No — same gap |
| Local patch + pinned build | Possible next session; draft only here; not CI-wired |

## Blocker

**Wait upstream** for virt `TYPE_NMI`→async SError, **or** sponsor-approve a **pinned QEMU commit/build** carrying a reviewed local patch, then re-probe + require `el0: serror` under EXPECT.

Until then: park Verified; do not require `el0: serror`; do not claim taken Verified.
